Publish a tool docs book

Use when an agent team needs to publish a tool book, solo and trio autorun scripts, and pages under lmctl.com/tools/NAME.

Purpose

This checklist publishes a tool book at lmctl.com/tools/NAME/ and generates solo/trio provider scripts. Follow it from top to bottom.

Checklist

  1. 1. Prepare an isolated website clone

    Read tools/README.md and durable-memory/tools-docs.md; check package.json, the current generator and deploy workflow. Work in your own lmctl clone when the shared worktree is dirty or used by other teams. Review the staged diff and run git pull --rebase origin main before every push.

  2. 2. Verify release and authorization

    Confirm public GitHub repo, owner, tag, source revision, schema and supported platforms. Test the released binary: its documented version output must identify NAME and the exact X.Y.Z from the tag; allow documented build or dependency details after that version. Do not require a single-line output. --dsl-schema --json must match the repo schema bytes; compare --dsl-signatures if supported. Probe install="github:lmctl-ai/NAME@latest" from an empty LMSCRIPT_TOOL_CACHE, for this machine's OS and architecture; verify checksum and an expected-output run. Require a tag guard that refuses a tag/version mismatch and green CI on all release platforms.

    For LMCode hosts, choose from the five-language SDK family: C++, Rust, Go, C#, and Java. Their default registries provide standard functions automatically. The canonical std/lmcode-std.schema.json defines 72 signatures; keep host-owned schemas and registrations limited to host-specific calls. The C++, Rust, Go, and C# READMEs say to merge std declarations into effective compiler input until compiler injection is available. The Java README documents its default and empty registry forms but not compiler-schema merging; check that runtime's compiler guidance instead of assuming the same schema flow.

    Every tool release must publish a SHA256SUMS asset containing checksums for its binary release assets. Generate it after all platform artifacts are assembled and before publishing. For NAME-prefixed binaries and archives, use this workflow step; exclude per-asset .sha256 sidecars:

    - name: Generate release checksums
  run: |
    cd dist
    find . -maxdepth 1 -type f -name 'NAME-*' ! -name '*.sha256' -printf '%f\0' | sort -z | xargs -0 sha256sum > SHA256SUMS

    Use dist/* in the existing gh release upload or gh release create command so it attaches SHA256SUMS with the binaries. Each manifest line uses sha256sum format: 64 hexadecimal SHA-256 characters, two spaces, then the exact asset filename. Hash each binary and packaged archive once; exclude licenses, notices and checksum sidecars. Backfill only when authorized, after downloading current assets and verifying each hash against the GitHub release API digest.

    If the Lead explicitly authorizes public tool-repo and release work, the assigned team may add missing version/schema/install support and a tag guard, then cut a release after all platform CI passes. Ask the tool owner when the task is website-only or dogfood-only, release work is not explicitly authorized, the team lacks repo/release authority, or ownership is unclear. Never publish against an unguarded or guessed release. If a fresh GitHub API lookup returns 403, record the empty cache, export GITHUB_TOKEN from gh auth token, retry, and report the tested OS, architecture and checksum. A warm-cache hit is not fresh-install evidence. The website runner resolves lmhtml through its install declaration; if that lookup is rate-limited but a previously verified release binary is cached, set LMHTML to that binary for local checks and record that this was a cache fallback, not a fresh install.

  3. 3. Make examples self-contained

    Each selected LMScript teaches one concept, uses deterministic synthetic inputs or bundles its fixtures, runs from an empty temporary directory, and has a repository expected-output check for values, text, image dimensions, mesh properties or stable export signature. Keep examples compact: rendering times out at 180 seconds. When lmscript calls a renderer with system(), pass an explicit timeout in milliseconds; command-literal system calls use a 60-second default and can stop valid renders too early. Keep the host timeout above the render budget but below the generator limit. Choose a smaller example or check in a provenance-verified preview if it is too slow.

    Quickrun examples save bytecode to a predictable variable and pass it to savedsl; for example, out = ARGV.len() > 0 ? ARGV[0] : "build/name.dslb", then savedsl(program, out). Inspect generated source: the generator can derive out from savedsl and avoids a duplicate host run when one is already present; hard-coded output paths need a matching renderer. Guard each setup statement separately so a build-directory guard does not skip other assets.

    List examples in examples/README.md or tools/NAME/book.json with unique slug, safe source path, description and rendered output. Verify sources exist at the selected release revision. Text outputs are UTF-8 and may use captured .txt or .csv files with preformatted previews. For non-visual tools, execute and assert the real output first; any PNG card must visualize that data and say it is a preview, not an image produced by the target.

  4. 4. Fill book data and author manual pages

    Set tools/NAME/book.json with display name, repo, description, a concrete domain task, solo/trio members, selected examples, and exactly three absolute lmctl.com links: LMScript LMCode docs, concise tool API summary, and a simple generated example. Each example prompt links its own page. Keep shared prompts tool-neutral: Coder reports task outputs and checks; Reviewer assesses those against the Lead's checklist.

    Author tools/NAME/get_started.html manually; the generator does not create it. Start with an Overview section, add a logo figure pointing to img/logo.png, verify commands from a fresh directory and link the hosted scripts with absolute URLs. Include an examples manifest and expected-output tests in the tool repo when practical; use explicit book metadata if it has no examples catalog.

    Generate with TOOL=NAME REF=main npm run sync:tool-examples. For a local repo set SOURCE_DIR and SOURCE_REF; use OUTPUT_DIR for scratch output. Pages, sources, previews or text results land under tools/NAME/examples/. The generator rewrites a local schema declaration to the released cli plus install declaration when needed; inspect generated source. Slug names the page; configured file path names the source link, including nested sources. Add a regression check for nested source links. Keep generated prompt labels and URLs on separate lines. Run TOOL=NAME python3 scripts/tools/generate-quickruns.py for tools/NAME/NAME_solo.lms and NAME_trio.lms; OUTPUT_ROOT redirects output.

  5. 5. Update curated catalogs

    Add two unique entries with absolute script URLs to scripts/autorun-examples.json. This is the input; do not edit generated autorun/index.txt or autorun/index.html. Run node scripts/build-onboarding-catalogs.mjs to generate those files plus helloexample/index.txt and helloexample/index.html. Tool demos belong in autorun, not the hello-only list.

    Generated scripts start with autorun-role headers for alias, provider and model; the body uses @role(Alias.provider) and @role(Alias.model). Solo has Lead. Trio passes Lead's assignment to Coder, Coder's result to Reviewer, then both to Lead. Start lmctl prompts sequentially; concurrent starts can hit SQLite database is locked.

  6. 6. Create and QA the tool README

    Keep README.md scannable: relative-path hero, one-line pitch, at most three badges, feature gallery, architecture/flow diagram, short quick start, links to get started, guide, API summary and releases, plus Build and test, Third-party notices and license sections. Include required company attribution; never add personal email.

    Choose a distinctive hero with the owner. Keep image sources in docs/readme/*.lms and regenerate them with docs/readme/render.sh. Artwork scripts should declare the released renderer through install= and the render script should reuse one verified cache rather than repeatedly resolving releases. Every image, including gallery and diagram, needs light and dark assets with theme-aware selection. Keep each under about 400 KB. Prefer ASCII labels; otherwise verify glyph coverage in the font and inspect the final PNG.

    Show three to six examples, captions linked to source and generated book page. Ensure every README gallery slug is selected in tools/NAME/book.json and that its generated page exists before pushing the README. Use two columns; when count is odd, make the final tile full-width. For numerical or text tools, run and assert the example, then draw a labeled card/chart from its checked output using lmdraw or another renderer. State which tool rendered the image. A headless tool's architecture diagram may use lmdraw and the target's real schema, engine and output flow; label the renderer honestly.

    Use three short quick-start lines and a curated alias when available; split long commands and avoid full URLs in narrow code blocks. Review at 1280-pixel desktop and 390-pixel mobile widths, with readable hero, captions and commands and no horizontal scroll. Use a compact mobile composition if text shrinks. Render from scratch with relative output paths and honor the exact bytecode path used by savedsl; a general renderer for arbitrary hard-coded targets is still an open improvement.

    After pushing the tool repo, inspect its actual GitHub README at desktop and 390-pixel mobile widths in light and dark themes. Check images/theme selection, glyphs, captions and links, required sections, wrapping and clipping. Compare each reported defect with the exact pushed commit and source before changing it; QA can describe stale coordinates. Fix for at most two rounds. If agy QA is out of quota, ask the Lead to run visual QA with Opus via helpers.lmctl and Playwright; retain screenshots and record browser/viewport.

  7. 7. Build a complete scratch site

    Copy the existing tools tree, scripts/tools, homepage/index.html and lmscript-site content at the matching site path before full-tree checks. Existing tools pages link to the lmscript site. Overlay generated pages and quickruns and run from scratch-site root.

    scratch=$(mktemp -d)
mkdir -p "$scratch/site/scripts"
cp -a tools "$scratch/site/tools"
cp -a scripts/tools "$scratch/site/scripts/tools"
cp -a lmscript-site "$scratch/site/lmscript"
cp homepage/index.html "$scratch/site/index.html"
SOURCE_DIR=/path/to/NAME SOURCE_REF=$(git -C /path/to/NAME rev-parse HEAD) \
  OUTPUT_DIR="$scratch/site/tools/NAME/examples" TOOL=NAME npm run sync:tool-examples
OUTPUT_ROOT="$scratch/site/tools" TOOL=NAME python3 scripts/tools/generate-quickruns.py

    Run scripts/tools/run.sh check with no argument for the full tools tree. Its optional argument is one HTML file, never a directory. For every page in a tool folder, run lmhtml lint --config scripts/tools/plain.conf tools/NAME and inspect findings. In scratch use the copied runner from scratch root. Run the onboarding builder only from the complete website clone, not a partial scratch copy.

  8. 8. Review generated pages and artifacts

    Use the plain-text HTML lint profile. Check overview, get-started page, examples index and every example page; follow links, confirm destination pages exist, compare captions with outputs. For CAD/STL, check triangle count, edge multiplicity and mesh volume. Report all non-manifold edges; never call an STL print-ready unless watertight.

    Use browser QA on scratch overview and examples index at 1280 by 900 and 390 by 844. Retain screenshots and check light/dark themes, images, wrapping, captions, links and overflow. If adding a tools-catalog item, add its logo/icon through scripts/tools/icons and check iconed and un-iconed neighboring rows align; authored overviews still need their own logo figure. Ask an independent Review member to inspect the staged website diff and resolve findings.

  9. 9. Publish, then run provider sessions

    Before publishing, validate syntax, generated sources, local outputs and expected checks. New lmctl.com links return 404 until deployment, so run providers after publish or use stable raw GitHub links in a documented pre-publication prompt. Do not treat a pre-deployment 404 as a release failure.

    Confirm lmctl help autorun succeeds and use an autorun-enabled CLI. From an empty temporary directory run solo and trio sequentially with --non-interactive when role mappings are ready; this skips the optional post-report terminal handoff. Open a terminal separately if needed. Verify solo output and all trio handoffs through Lead, Coder and Reviewer. Inspect real files/printed output and expected checks; save-only mappings do not prove model turns. For CAD, require the Reviewer to check STL watertightness.

    Headless run from the temporary directory: lmctl --non-interactive autorun ./tools/NAME/NAME_solo.lms, then lmctl --non-interactive autorun ./tools/NAME/NAME_trio.lms.

  10. 10. Run gates, record feedback and push

    Refresh generated catalogs and memory indexes, then run gates from the website clone. Feedback files follow plain-text Markdown: no inline code; fenced blocks only. Run memory-check before pushing feedback.

    lmhtml lint --config scripts/tools/plain.conf tools/NAME
npm run check:tools
npm run check:onboarding-catalogs
npm run check:skills
npm run check:memory

    Record unclear or wrong steps with evidence and a proposed correction in durable-memory/tool-book-feedback/NAME.md. Review and commit the staged diff, pull --rebase origin main, push, and wait for deploy-static. Then run scripts/tools/verify-live.sh tools and scripts/tools/verify-live.sh skills; both must report zero findings.

Known issues still open

  • lmpy dogfood reported interactive autorun can finish its report and then exit with “No deferred tool marker found” while opening the optional terminal. --non-interactive bypasses it; an lmctl runtime fix is unconfirmed.
  • The lmcad guide documents --schema, but its released host uses --dsl-schema; the tool owner should correct the guide.
  • The lmcad raised-rim STL review found four non-manifold contact edges. Keep the warning until repaired and watertightness is verified.
  • The shared decorator logo contract differs between generated fallback indexes and authored overviews; the manual workaround is to add the logo figure to authored pages.
  • Fresh GitHub release lookups may return 403 despite cached binaries. Authenticated retry and cache reuse work; an offline cached-host resolver is still wanted.
  • README artwork still needs tool-specific handling for sources with fixed savedsl output names; follow the declared target until a shared discovery helper exists.
  • The final lmdraw gallery-spacing correction came after its two allowed QA rounds; that small Markdown-only edit was not separately browser-reviewed.

Feedback loop

Every team records evidence, guesses, blocked prerequisites and proposed fixes in durable-memory/tool-book-feedback/NAME.md. Keep feedback plain text. The Lead reconciles findings into this checklist and marks each feedback file with its merge date.

Prompt for the next team: Follow this checklist from top to bottom for NAME. Work in your own lmctl clone, verify the release and self-contained examples, generate the book and scripts in a complete scratch site, prepare and visually QA the tool README at desktop/mobile widths in light/dark themes, then publish before provider runs that use new lmctl.com links. Run all gates, memory-check before pushing feedback, and record every unclear or wrong step in durable-memory/tool-book-feedback/NAME.md.
