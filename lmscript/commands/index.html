lmscript commands

Not one script per lmctl command — one USEFUL artifact per command, fetched by lmctl <command> ... --save-script <file>. Sometimes that's a script; sometimes, like plan, it's a document; sometimes, like lint, there's nothing to add. A metalead downloads what's here, edits it for the job in front of it, and runs it — a human reads the result, so each artifact stays simple enough to follow top to bottom.

Why this exists

Two tiers, both usable by a human or an LLM. The CLI — lmctl plan, lmctl lint, and so on — handles simple things directly, and restricts what either of you can do to exactly that: fine, right up until the job stops being simple. lmscript is what you switch to when it does — but only where it actually buys something. A script that just re-types a CLI command as an argv array has gained nothing; lmscript does not wrap the CLI. The real value is calling lmctl's own internals directly, which expose fine control the command line deliberately doesn't — lm_agent's first prompt, for example, is entirely yours to write, where lmctl seed/lmctl hello always send the same generic one. --save-script is the bridge to that, not a code generator: the point where the CLI stopped being enough and you continue from where you were.

Prerequisite

Every script dispatches to a real provider CLI. Run lmctl init once to detect which providers you have, and lmctl ratelimit any time to see which ones are actually working right now.

Available

  • plan.txt A document, not a script — plan's job is to produce a teamfile, so the useful artifact is real examples of the common shapes (solo, lead+reviewer, lead+coder+reviewer, multi-provider) to copy and adapt, not a program that builds one.
  • lint No script here on purpose. lmctl lint <file> is already the whole operation — there's nothing to compose around it.
  • seed.lms { provider, model?, preamble, out? } — constructs a new agent from scratch and sends preamble as its real first prompt, the fine control the CLI doesn't expose.
  • prompt.lms { teamfile, alias, prompt, acceptance: [...], out? } — one dispatch to an existing seeded member, evidence-checked.

Gaps, stated rather than papered over

Some useful scripts can't be written well yet because lmctl hasn't exposed the needed internal as a registered lmscript function — lm_plan, for a teamfile-building script that's more than a document, is the clear example. Where that's true, this page says so rather than reaching for system(["lmctl", ...]) to fake it; a wrapper that only re-types a command is worse than an honest gap, because it looks like a feature.

Alternatives

One artifact per command today. A second one for a command (a different shape of the same job) gets listed here next to the first, not silently swapped in.

Structure

Each script is a sample, not a service — short on purpose, with a one-line comment per step so reading just the comments tells you what it does. Everything is safe to edit; reshape it for the job in front of you.

Fetch

lmctl seed team.lmctl --save-script myseed.lms
lmctl script myseed.lms request.json

--save-script <file> runs the command as normal, and on success fetches the matching artifact here and writes it to <file> — requires @lmctl-ai/lmctl 0.2.14 or later (lmctl --version to check; npm install -g @lmctl-ai/lmctl@latest to update). --script <name> overrides which one to fetch, for an alternative. Older versions: curl the URL directly instead.

Request forms use <your-provider>, never ${Provider1}

A request form has no substitution step. ${Provider1} is for a .lmctl template quickrun expands — left in a request form, it reaches the provider registry literally and errors. Write "provider": "<your-provider>" and replace it before running.
