lmvideo guide

How lmvideo is put together and how to think about a program for it: the two languages in one file, the host owned surface and encoder, the retained drawing model, the two 3D render paths, physics as a baked take, and the limits that shape a script. Facts describe release v0.1.124.

Overview

lmvideo combines the lmscript host contract with Skia drawing and media output. A script configures a Canvas, Image, Plot, Panel or Scene3D and then draws still images or video frames through one author facing API. Canvas primitives, retained plots, explicit layout managers, diagrams, images, SVG and PDF documents and CPU rendered 3D scenes all compose on the same output surface.

The script chooses the dimensions and the output path. The host owns the drawing surface and the output lifecycle, calls ffmpeg from PATH for video encoding, and bundles DejaVu Sans so text metrics are consistent. The public repository holds examples, documentation, the schema and release metadata; the implementation sources are maintained separately and binaries are published as GitHub releases.

Two languages in one file

An lmvideo program is an ordinary LMScript file that contains a typed block. The outer script handles arguments, directories, other tools and control flow. The block, between the _lmcode_ header and end _lmcode_, is compiled by lmscript against the schema that the lmvideo binary publishes, and is executed by the host in one process.

LayerRuns inTypical content
Outer LMScriptlmscriptARGV defaults, mkdir, write_file for fixtures, run_lmcode, assert, optional system calls such as an ffmpeg GIF conversion
_lmcode_ blocklmvideo hostlet bindings, loops, typed functions, calls on canvas, video, out and the host functions
Splice ${name}compile timeCopies an outer value into the block, for example an output path or a frame count

Older documents and scripts used a block marker named _dsl_, a manual compile to a .dslb file and a direct lmvideo --lmcode run. The current form is the _lmcode_ block executed with run_lmcode; the bytecode stays internal. The host flags --lmcode-schema --json, --lmcode-signatures and --lmcode FILE remain the protocol that lmscript speaks to the host underneath.

png = ARGV.len() > 0 ? ARGV[0] : "images/image.png";
width = ARGV.len() > 1 ? num(ARGV[1]) : 640;
height = ARGV.len() > 2 ? num(ARGV[2]) : 360;
mkdir("images");
program = _lmcode_ cli="lmvideo" install="github:lmctl-ai/lmvideo@v0.1.124";
video.size(${width}, ${height});
video.frames(1);
video.output(${png});
video.begin();
video.frame();
canvas.clear("#101820");
canvas.circle(float(video.width()) * 0.75, float(video.height()) * 0.35, 60.0, paint().color("#ffd166"));
video.end();
end _lmcode_
r = run_lmcode(program);
assert(r.ok);

The video lifecycle

The lifecycle is explicit. Configure the video object, call begin, call frame once per loop iteration, draw, then call end. begin allocates the host owned surface; frame selects the next frame; end finishes the file. Calling frame outside begin and end is a host error.

  1. video.size, video.fps, video.frames, optionally video.crf, and video.output.
  2. video.begin.
  3. For each index up to video.count: video.frame, then drawing on canvas. video.t is the normalized position used by the examples for easing; video.time is the authored time in seconds; video.index is the frame number.
  4. Optionally video.save_frame to keep a poster image of the current frame.
  5. video.end.

A still image uses the same lifecycle with one frame and a PNG output path. Work that needs no frame at all can skip the lifecycle: a Surface, an Image or a recorded Document writes its own files.

Drawing model

Immediate canvas calls and retained objects

Canvas has immediate primitives (clear, rect, circle, line, path, text, image, svg) and transform state (save, restore, translate, scale, rotate, clip_rect). Paint, Path and Font values are built with fluent calls and passed to those primitives.

Plots, panels and diagrams are retained. canvas.plot returns a Plot that keeps its title, ranges and Series; drawing happens when draw is called. An animation therefore keeps one Plot outside the frame loop, clears and refills its series per frame, and calls draw, as the damped oscillator example does. A Panel arranges plots, text, shapes and images with a layout manager and draws them together.

Diagram shapes follow the vocabulary of the earlier lmdraw host: box, diamond, cylinder, note, cluster, connector, lifeline, message and group create nodes, attributes are adjusted with set_attr, and redraw followed by png renders the retained drawing. canvas.target points the canvas at a Surface for that workflow.

Images

Image is a mutable fluent value with processing, drawing, measurement and comparison methods. Layout composes several images in layers or as a sheet, and Timeline holds frames with per frame delays for GIF output. An Image returned by a renderer is not on screen until it is painted with canvas.image.

Vector and document output

document(width, height) records drawing into a Picture, which replays to PNG at a chosen scale, SVG, PDF or a serialized Skia picture. pdf_document collects pictures as pages. surface(width, height) is an off-screen raster target that can also export SVG and PDF. The vector outputs example in the repository round trips an emitted SVG through svg_file and a Surface.

SVG input

svg(text) and svg_file(path) parse SVG and canvas.svg places it in a target rectangle. The host parses and validates the supported SVG elements and attributes before rendering. Keep one explicit default namespace on the root and a viewBox; width and height are inferred from the viewBox.

3D: one scene, two render paths

A Scene3D holds meshes as nodes, materials, a camera, lights, shadows and an environment. The world is right handed with Y up. Meshes come from primitive builders, lathe, extrusion, text, heightfields, triangles or files; materials are PBR values with optional textures.

PathCallUse
Rasterscene.render_image(width, height, samples)Fast CPU preview for shaping a scene, checking a camera or scrubbing an animation. Depth and normal images are raster passes.
Cyclesscene.render_image(width, height, "cycles", samples, bounces, seed, denoise)CPU path tracing for the final image, with optional Open Image Denoise.

Keep one scene and change only the render call when comparing the two. Camera, meshes, transforms, materials, lights, environment and animation time are shared. A beauty image comparison between the paths is descriptive: differences in indirect light and denoising are expected. The renderer name is explicit, so a build without Cycles reports an error instead of substituting a raster image; render_available("cycles") lets a script check first.

For a moving scene, set scene.time(video.time()) before each render. For long sequences, scene.save_job writes a bounded, versioned job that the lmvideo render-job and render-job-batch commands render outside the script; batch output is atomic, frame IDs are numeric and stable, and a result manifest records each frame's settings and checksum.

The Cycles profile rejects input it does not support instead of dropping it: screen space Gaussian sprites, non-opaque materials, mixed U and V wrapping, non-unit occlusion maps and per object shadow overrides. Keep those on the raster path. scene.threads sets the worker count; keep it fixed for repeatability checks.

Physics as a baked take

lmvideo uses Jolt Physics on the CPU. Boxes and spheres live in a fixed step world that shares its coordinates with Scene3D. Units are metres, kilograms and seconds; mass zero makes a body static; friction and restitution range from 0 to 1. world.planar(true), chosen before bodies are added, constrains motion to X and Y translation and Z rotation.

Render geometry is separate from colliders: the script adds a mesh node for each body and matches its dimensions to the collider, floors and ramps included. body.sync(node) or pose.sync(node) copies position and rotation onto the node without squashing its mesh. Parented, keyframed or detached nodes refuse synchronization.

world.bake(frames, stride) records the current poses and advances the world forward; the resulting PhysicsTake is immutable. take.pose(t, body_id) interpolates for t between 0 and 1. The repository loops replay a take through a smooth periodic phase, the square of sin(pi * frame / frame_count). That is time replayed physics with forward and backward playback: the solver never integrates backwards, and a duplicated first frame after a discontinuous last frame is not a seamless loop.

physics_presentation builds presentation content from physical parts in top left pixel coordinates: letter tiles, stacked bar units, bullet balls and KPI heaps. step advances it, render returns an Image, tumble removes the floor and launches the content, assemble restores the authored poses.

A working rhythm

  1. Start from the closest repository example or book chapter and keep its block header.
  2. Compile with lmscript --check after each edit. The compiler names unknown methods and lists the valid ones.
  3. Run small: low resolution, few frames, raster rendering, few samples.
  4. Look at the PNG, or a saved poster frame of the video, before raising quality.
  5. Switch the render call to Cycles and raise samples only for the final still or bounded batch.
  6. Record what matters with out.print and assert on r.ok in the outer script.

Standard library and the newer REST and CLI interfaces

Every lmcode host carries the shared standard catalog next to its own functions. lmvideo v0.1.124 pins the lmcode_std_v3 edition with 206 signatures: string, math, file, JSON, template and result envelope functions and the typed list, map, queue, stack and priority queue containers. They need no import.

The current lmcode_std_v3 catalog has grown to 226 signatures by absorbing the former lmcode_std_rest_v1 module: the interfaces RestGet, RestPost, RestPut, RestDelete, RestPatch, RestHead, RestOptions, RestHandler, CliCommand and CliOption, the functions rest_config, rest_route, rest_serve, rest_stop and rest_cli, and the RestExchange type. lmvideo v0.1.124 does not provide these. A program that calls one of them is refused by the host at load time with code LOAD_UNBOUND. They become available in lmvideo when a later release is built against the 226 signature catalog; the reference page lists them with that status.
