lmscript commands

One canonical .lms script per lmctl command, fetched by lmctl <command> ... --save-script <file>. lmscript is the LLM's command line: a metalead downloads one of these, edits it for the job in front of it, and runs it — a human reads the result to see what happened, so each script stays simple enough to follow top to bottom.

Why this exists

Two tiers, both usable by a human or an LLM. The CLI — lmctl plan, lmctl lint, and so on — handles simple things directly, and restricts what either of you can do to exactly that: fine, right up until the job stops being simple. lmscript is what you switch to when it does: save the job to a file, edit it, run it. The restriction lifts there — an LLM can write a script about as fast as a person types a long command's worth of flags. --save-script is the bridge between the two: not a code generator, not a convenience, just the point where the CLI stopped being enough and you continue from where you were instead of starting over.

Prerequisite

Every script dispatches to a real provider CLI. Run lmctl init once to detect which providers you have, and lmctl ratelimit any time to see which ones are actually working right now.

Available

  • plan.lms { dir, name?, pattern?+provider?+model?, members?, force? } — writes a teamfile.
  • lint.lms { teamfile } — structured error/warning summary.
  • seed.lms { teamfile } — creates real provider sessions, verified against the file.
  • prompt.lms { teamfile, alias, prompt, acceptance: [...], out? } — one dispatch, evidence-checked.

Alternatives

One script per command today. A second script for a command (a different shape of the same job) gets listed here next to the first, not silently swapped in.

Structure

Each script is VALIDATE / DISPATCH / VERIFY (or GUARDS), marked with // ==== ... ====. DISPATCH is the edit surface — replace it for the job in front of you. Don't move VALIDATE or the block after DISPATCH; that's what makes a bad form or a bad reply fail loud instead of silently.

Fetch

lmctl plan ./backend --pattern 3 --provider <your-provider> --save-script myplan.lms
lmctl script myplan.lms request.json

--save-script <file> runs the command as normal, and on success fetches the matching script here and writes it to <file> — requires @lmctl-ai/lmctl 0.2.14 or later (lmctl --version to check; npm install -g @lmctl-ai/lmctl@latest to update). --script <name> overrides which script to fetch, for an alternative. Older versions: curl the URL directly instead.

Request forms use <your-provider>, never ${Provider1}

A request form has no substitution step. ${Provider1} is for a .lmctl template quickrun expands — left in a request form, it reaches the provider registry literally and errors. Write "provider": "<your-provider>" and replace it before running.
