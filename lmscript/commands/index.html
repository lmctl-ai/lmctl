lmscript commands

One curated .lms script per lmctl command — fetched automatically when you run lmctl <command> ... --save-script <file>. lmctl only contributes the name and the download; these scripts are ours, authored and improvable without shipping a release.

Prerequisite

Every script here dispatches to a real provider CLI. Run lmctl init once to detect which providers you have, and lmctl ratelimit any time to see which ones are actually working right now. Without a configured provider, none of these have anything to run against.

Available scripts

  • plan.lms Generate a teamfile from a request form instead of wizard prompts or one-shot flags — a team composition becomes data you keep, diff, and re-run.
  • lint.lms Validate a teamfile and get a structured pass/fail summary (error count, warning count, each message) instead of parsing lint's text output yourself.
  • seed.lms Create real provider sessions for a teamfile, verified by reading the file back afterward — seed's exit code alone isn't proof a session exists.
  • prompt.lms Send one prompt to one seeded member with acceptance criteria attached — the reply has to address each one with evidence, not just claim success.

Alternatives

Only one script per command exists today — this is a starting set, not the whole shape of the idea. The plan is more scripts per command for cases the canonical one doesn't cover well (for example, a plan variant driven by an existing teamfile as a template, or a prompt variant that fans out to several workers and consolidates their replies). When a second script for a command ships, it'll be listed here next to the first with what distinguishes them — not silently added.

Try one

Fetch one directly and run it with a request form — this works today:

curl -O https://lmctl.com/lmscript/commands/plan.lms
lmctl script plan.lms request.json

lmctl <command> ... --save-script <file> is the shorthand for the fetch step above, coming soon — it downloads the matching script here and writes it to the file you name, nothing more. Until then, fetch the URL directly.

Request forms — real provider, not a placeholder that resolves itself

Each script takes one argument: a path to a request-form JSON file. Unlike a .lmctl teamfile template fetched by quickrun, there's no substitution step for a request form — lmctl script hands whatever you write straight to the provider. So a request form never writes ${Provider1}; it writes an unmistakable blank instead:

{ "dir": "/path/to/your/project",
  "pattern": "2",
  "provider": "<your-provider>" }

Replace <your-provider> with something lmctl ratelimit actually shows you have. A literal ${Provider1} here would look like it resolves and then fail at runtime with a confusing registry error instead of an obvious blank to fill in — see the lmscript workflow skill for the full reasoning and the language itself.
