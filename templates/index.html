lmctl templates

Team compositions worth trying, one .lmctl file each — fetch one with lmctl quickrun <url> to try it right away. The point is the variety of shapes, not any one file: start here, then read how a teamfile works to shape it into what you actually need.

Available templates

  • solo.lmctl — one member, no delegation. The smallest possible team.
  • pair.lmctl — Lead + Reviewer. A second opinion before anything ships.
  • trio.lmctl — Lead + Coder + Reviewer. A solid default for most real tasks.
  • qa-squad.lmctl — Lead + Coder + Reviewer + QA. Adds an end-to-end verification pass.
  • triple-review.lmctl — one Lead, three independent reviewers across different providers.

Try one

lmctl quickrun https://lmctl.com/templates/trio.lmctl

This fetches the file, fills in your own providers/models (see below), creates provider sessions, and drops you into a chat with the team — no editing required first.

The ${Provider1..3} / ${Model1..3} convention

A published template has to work for any user, regardless of which providers they have — so a template never names a real provider. Instead of provider=claude, every template writes provider=${Provider1} (or ${Provider2}, ${Provider3}), and instead of model="claude-opus-5" it writes model="${Model1}" (paired with the same-numbered provider). lmctl init records which providers you actually have and your top three models; lmctl quickrun substitutes those into the placeholders before seeding.

A user with three configured providers gets three genuinely different _MEMBER_ lines. A user with only one provider configured just has every slot resolve to that same provider — the file still runs, it's simply less diverse. That portability is the entire point: the same template file works for both users unmodified.

quickrun accepts any URL or local path, not just the ones on this page — these are examples, not a walled garden. If you're writing your own template:

  • Only ever write ${Provider1}, ${Provider2}, or ${Provider3} as a provider= value — never a real provider name.
  • Pair each provider slot with the same-numbered model slot: a member using ${Provider2} should use model="${Model2}", not ${Model1} or ${Model3}.
  • A slot can back more than one member (see qa-squad.lmctl, where QA reuses ${Provider1}) — you aren't limited to three members just because there are three slots.
  • Everything else about the file is a normal teamfile — see the teamfile format page for the full _MEMBER_ line grammar.
  • An unrendered template (with literal ${Provider1} still in it) will fail lmctl lint — that's expected; it's meant to be fetched and substituted by quickrun, not linted directly.
