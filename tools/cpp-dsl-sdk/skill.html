lmcode-cpp host authoring skill

This lmcode-cpp page is also kept at its former address for existing links; the current address is /tools/lmcode-cpp/.

Purpose

Guide the creation of a small C++17 host that exposes a typed schema to lmscript and loads and runs _lmcode_ bytecode with the lmcode-cpp header include/dslvm.hpp.

When to use it

Use this when implementing a native application that should expose a controlled set of host objects, methods and functions to _lmcode_ blocks, or when checking that an existing host still matches its schema and the standard catalog.

Install

Vendor include/dslvm.hpp together with every stdlib/*.hpp file from the SDK and compile as C++17; there is no library build and no third-party dependency. Use a published lmscript compiler from the @lmctl-ai/lmctl npm package that emits bytecode version 6.

npm install -g @lmctl-ai/lmctl
git clone https://github.com/lmctl-ai/lmcode-cpp

Every default dslvm::Registry includes the lmcode_std_v3 standard catalog: 226 canonical signatures (88 functions and 138 methods on 17 standard types), pinned in std.lock as version 3 of std/lmcode-std.schema.json. Registry(StdMode::Disabled) opts out and dslvm::register_std(registry) enables it idempotently.

Commands

g++ -std=c++17 -Iinclude host.cpp -o host
lmscript --lmcode-signatures schema.json
./host --lmcode-signatures
./host --lmcode scene.dslb
python3 scripts/merge-std.py host.schema.json effective.schema.json
make test
make conformance

The merge-std.py helper in the SDK repository generates the effective compile and load schema from a host-only schema plus the standard catalog. The make targets run in the SDK checkout.

Inputs and outputs

  • Input: binary bytecode and the exact JSON schema bytes used to compile it.
  • Host setup: registry callbacks plus context pointers to host-owned objects.
  • Output: host-defined effects and, for command-line programs, one standard JSON result line that run_lmcode returns as ok and result.

Tool users write a block against a released host and execute it with run_lmcode:

prog = _lmcode_ cli="X" install="github:lmctl-ai/X@latest";
...
end _lmcode_
r = run_lmcode(prog);

SDK authors developing a host compile against a local schema file and save the bytecode:

p = _lmcode_ schema="schema.json";
g.say("Hello from lmcode");
end _lmcode_
savedsl(p, "demo.dslb");

Safety rules

  • Treat bytecode as trusted: the VM does not impose runtime limits or dynamic call checks.
  • Pass exact schema bytes and bind each host-specific context, function and method; standard functions are included by the Registry.
  • Keep objects and references returned by methods alive for all subsequent script calls.
  • Check signature parity during development. Matching arity and return type are part of the schema contract.
  • Return standard collection values from native callbacks only through registry.std_collections(); they are valid for the current run.
  • The standard catalog includes file_read, file_write and file_append on native paths and the rest_serve server; opt out with Registry(StdMode::Disabled) when a host must not offer them.

Worked examples

  1. Create one Registry and register a context object type.
  2. Bind each method callback with argument and return type strings that exactly match the schema.
  3. Load bytecode and schema bytes with Program::load.
  4. Create host objects before Context::set; keep owners in scope through Program::run.
  5. Use standard functions without host registration; bind only host-specific functions and methods.

The tutorial builds a complete greeter host; examples/rest_serve.cpp and examples/rule-entries.lms in the repository show the REST surface and annotated interface entries.

The catalog includes the standard REST and CLI surface: the 10 interfaces RestGet, RestPost, RestPut, RestDelete, RestPatch, RestHead, RestOptions, RestHandler, CliCommand and CliOption (each takes one RestExchange and returns void), the functions rest_config, rest_route, rest_serve, rest_stop and rest_cli, and 15 RestExchange methods.

Errors and exit codes

Catch dslvm::Error around load and run. Standard CLI conventions use exit 2 for compilation or argument errors, 3 for bytecode load or run errors, and 4 for application failures. Include the error code and source location when present.

How to verify

  1. Compile a tiny _lmcode_ block against the host schema.
  2. Diff the compiler signatures against Registry::signatures().
  3. Test a valid run and representative load and runtime failures.
  4. Confirm the host passes the exact schema bytes used by the compiler.
  5. Test object ownership and collection access over the complete script run.
  6. In the SDK checkout run make test and make conformance.
