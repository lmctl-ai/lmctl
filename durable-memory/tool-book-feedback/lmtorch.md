# lmtorch publish-tool-book dogfood feedback

## Prerequisites

- Step: Release prerequisite check and release instructions. The skill says to stop and ask the tool owner to cut a guarded release, while this assigned run explicitly permits adding missing release support and cutting after CI. Proposed wording: If the assigned scope authorizes release work, add the missing host protocol and tag guard, wait for all platform CI jobs to pass, then cut the release. Otherwise stop and ask the owner.
- Step: Install probe. The skill's example names NAME_BIN and expects a compatible executable but does not explain selecting the correct platform asset. On this ARM64 host, the Linux x64 asset downloaded correctly but failed with Exec format error. Proposed wording: Choose the release asset matching the operator's OS and architecture; record the architecture and verify the downloaded file before execution.

## Book generation and catalogs

- Step: Curated autorun entries. The skill says to edit autorun/examples.json, but the repository's input is scripts/autorun-examples.json; autorun/ only contains generated catalogs. Proposed wording: Add entries to scripts/autorun-examples.json; run node scripts/build-onboarding-catalogs.mjs to generate autorun/index.txt and autorun/index.html.
- Step: Preview assets. The generator requires each selected example to have a PNG preview or a rendered PNG output. This is not explicit for non-visual tools such as lmtorch, whose example output is numeric. Proposed wording: For non-visual tools, provide a small checked-in PNG preview that illustrates the example's data, map its filename under images, and describe it in the page caption; do not claim the program itself rendered that preview.
- Step: Example source mapping. An explicit examples item supports a file value separate from slug, but the generator then used the source filename stem as the slug and rejected the documented mapping. I fixed this minimally in scripts/tools/generate-example-book.py and verified the lmtorch source names tensor-sum-dsl.lms and autograd-gradient-dsl.lms generate pages tensor-sum.html and autograd-gradient.html. Proposed wording: The slug controls output page names; file may be any safe .lms path below examples/.
- Related generator improvement: The shared quickrun template told every Coder to make a drawing and render a PNG, which is wrong for tensor tools. I changed the shared prompt wording to ask for the assigned task's outputs and verification, then regenerated and syntax-checked the lmtorch scripts and scratch lmdraw scripts. Proposed wording: Ask the Coder to complete the assigned task and report its outputs and verification; ask the Reviewer to assess those results against the Lead's checklist.
- Related example-book defect: Each copied prompt linked the book's same simple example, even when the page described a different example. I added one short Example link to the current page and kept the canonical simple-example link in surrounding page text only when it differs. Proposed wording: Use one concise page-specific Example URL in the prompt; show the canonical simple-example link separately only when it is a different page.
- Related icon contract gap: tools/README.md says logo.png appears after an authored overview h1, while the decorator only inserts a logo into its generated fallback index. I left other tools' authored pages unchanged per the scope boundary. Proposed correction: either make authored-index logo insertion targetable and test it, or clarify that only generated fallback indexes receive the logo.

## Quality gates

- Step: Scratch dry run. The copy recipe omits the root lmscript/ tree, which contains a local target for a link from tools/lmscript/index.html. The scratch check reports that unrelated link as broken even though the real checkout passes. Proposed wording: Copy lmscript/ into the scratch site when the copied tool pages link to /lmscript/ paths.
- Step: Targeted checker invocation. The skill says scripts/tools/run.sh check tools/NAME, but the optional argument is loaded as a single HTML file; passing a tool directory fails. Proposed wording: Run scripts/tools/run.sh check from the site root to check the complete site, or pass one HTML file as the optional argument.
- Step: get_started page contract. The brief calls get_started.html a quickrun landing page, but the checker currently applies the guide requirement that its first h2 is Overview. Proposed wording: Although get_started.html is labelled Quickruns in navigation, it follows the guide content rule and starts with an Overview h2.
- Step: Visual QA. The skill says to open pages at desktop and mobile widths but gives no browser or screenshot procedure. Proposed wording: Use a browser capable of rendering the local scratch site; capture the overview and examples index at 1280 px and 360 px, inspect both screenshots, and record the browser and viewport.
- Step: Tool catalog visuals. Desktop and mobile QA exposed a missing catalog icon for a new tool, which left its entry misaligned. The skill does not mention the established icon pipeline. Proposed wording: For a balanced tools catalog, add a tool-specific icon script, render the 256 px logo and 64 px icon through scripts/tools/icons/render.sh, and run its --check gate.
- Step: Review workflow. The skill asks for an independent live seat but does not give the repository-specific way to invoke a team reviewer. Proposed wording: Ask the assigned Review member to inspect the exact site diff with the team's lmctl prompt command; have Review fix its findings, then review the revised diff.

## Release and live-run ordering

- Step: install=...@latest clean-cache probe. An anonymous GitHub API rate limit returned HTTP 403 before the release could be checked. Proposed wording: If a clean-cache install fails with a GitHub API 403, retry with an authenticated GITHUB_TOKEN and record that the cache was empty before the run.
- Step: Real solo/trio provider runs. Running before the new book pages are deployed yields 404s for the required references. Proposed wording: After publishing, run both provider scripts against the live URLs, then run verify-live and require zero findings.
- Step: Book source provenance. The examples were added after the existing release tag, so the preexisting release could not provide their tagged source files. Proposed wording: Ensure every configured example source exists at the selected release tag; if not, wait for green CI, cut a matching versioned release, and regenerate the book using that tag.
