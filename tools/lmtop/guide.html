lmtop guide

Overview

lmtop reimagines the traditional interactive top utility as a deterministic, cross-platform stdio JSON server for automated agents, benchmarks, and observability pipelines. Instead of rendering ANSI escape sequences to a terminal, it samples 24 host-normalized CPU, memory, disk, and network metrics on a background thread and answers structured NDJSON queries over stdin and stdout.

Sampling architecture and ring buffer memory model

The server separates periodic metric collection from request handling so slow or bursty client queries never jitter the sampling clock:

  • Absolute tick schedule: On startup, Monitor::start captures an initial baseline snapshot of CPU, disk, and network counters and launches a dedicated sampling thread. The thread sleeps until absolute steady-clock deadlines (sleep_until(started + k * interval)). If host load causes the thread to miss one or more deadlines, it skips ahead to the next future grid point rather than burst-catching up, and increments status.missed_ticks.
  • Warm-up synchronization: Because rate metrics require a measured time delta (dt_s) between two counter snapshots, the first sample is recorded one interval after startup. If a client sends a now query before the first tick completes, the server waits up to two intervals on a condition variable so one-shot callers receive a populated sample immediately.
  • Bounded in-memory history: Each sample is stored as a fixed-size C++ Sample struct containing wall-clock unix_ms, measured dt_s, 24 double-precision values, and four per-group error strings. The ring buffer capacity is governed by --cap-mb (default 100 MiB, divided by sizeof(Sample)); when full, the oldest sample is evicted in O(1) time.
  • Signal and EOF handling: On Linux, SIGINT and SIGTERM are masked on the background sampling thread and handled on the main polling loop so signals, stdin EOF, or a {"method":"stop"} request all join the sampling thread and exit cleanly with code 0.

Cross-platform metric parity and honest missing values

lmtop shares its 24-metric catalog and normalization rules with lmdebug's sys sample / sys counters specification across three native OS backends selected at compile time:

  • Linux backend (src/procfs.cpp): Reads aggregate and per-core CPU ticks from /proc/stat, memory and swap availability from /proc/meminfo, block I/O counters from /proc/diskstats filtered by /sys/block and /sys/class/block eligibility rules, non-loopback interface counters from /proc/net/dev, and 10-second Pressure Stall Information (some avg10) from /proc/pressure/{cpu,memory,io}.
  • Windows backend (src/sys_win.cpp): Queries PDH (\Processor, \PhysicalDisk(*), \Network Interface(*)) and GlobalMemoryStatusEx, rebasing per-tick rates into pseudo-counters so the shared delta engine computes identical percentages and rates.
  • macOS backend (src/sys_mac.cpp): Uses Mach host_processor_info for per-core CPU ticks, sysctl and host_statistics64 for memory and swap, IOKit block-storage statistics for disk throughput and IOPS, and getifaddrs (AF_LINK) for network interface counters.
  • Disk deduplication and counter integrity: To prevent double-counting block I/O, lmtop excludes loop, ram, and zram devices, partitions, and stacked devices where both a partition and its device-mapper target or aggregate parent appear. If any counter moves backward (such as an interface reset) or a metric is unsupported on the host OS (such as PSI outside Linux or disk.max_util_pct on macOS), lmtop emits -1 rather than fabricating zeros.

Window statistics and downsampled history

Clients can query the accumulated ring buffer at any time without disturbing ongoing collection:

  • Time-series history and stride downsampling: The history method accepts optional seconds (0 = entire buffer) and max_points parameters. When total samples in the window exceed max_points, lmtop computes stride = ceil(total / max_points), emits every stride-th row, and always appends the newest sample row if it did not land on a stride boundary.
  • Welford window summaries: The summary method aggregates each of the 24 metrics over the requested seconds window, skipping any -1 (missing) entries. For every metric with n > 0 valid samples, it returns n, min, mean, median, p95, p99 (type-7 linear interpolation percentiles), max, sample standard deviation (Welford's online algorithm), first, and last.

Combining lmtop with LMScript and load tests

In LMScript performance workflows, start lmtop server redirected to a pair of POSIX FIFOs before executing an lmcurl load test, lmvalkey benchmark, or lmrg corpus search. Once the workload finishes, invoke lmtop client --in ... --out ... summary to capture the exact host CPU peak, hottest single core percentage, disk write bandwidth, and memory pressure during the run, then send stop to terminate the monitor cleanly.
